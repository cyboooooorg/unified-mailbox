# Internationalization Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps
> use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One language setting per server, stored in SQLite and served
by the API, that the client UI follows (Paraglide, English and French)
and that the classifier will receive.

**Architecture:** `domain::Language`, a typed `SettingsRepository` port
on a key/value `settings` table, three use cases, `GET/PUT
/api/v1/settings/language` and a `settings_changed` SSE event. In the
client, Paraglide message functions replace every hard-coded string, a
small reactive locale holds the current language, and a sync function
aligns it with the server on every stream (re)connect and on
`settings_changed`.

**Tech Stack:** Rust (axum, utoipa, sqlx/SQLite), SvelteKit 3 SPA,
Svelte 5 runes, `@inlang/paraglide-js` 3.x, `Intl`, Vitest (node
environment).

**Spec:** `docs/superpowers/specs/2026-11-27-i18n-design.md`

## Global Constraints

- Languages: `en` and `fr` only; `en` is the base locale, the fallback
  and `Language::DEFAULT`.
- The server never sends a sentence for the user; `ErrorDetail.message`
  stays an English developer message the client never shows.
- No `params` field on `ErrorDetail` in this branch.
- No runtime `eval`; `npm run check:csp` must pass; no `style=`
  attribute (the CSP has no `style-src`).
- `src/lib/paraglide/` is generated and git-ignored.
- Language names in the picker are written in their own language
  (`English`, `Français`) and are not translated; `Unified Mailbox` is
  not translated.
- Every API change regenerates `api/openapi.json` (`mise run openapi`)
  and `client/src/lib/api/schema.d.ts` (`npm run generate`) in the same
  commit.
- Test data is invented. Commits follow Conventional Commits with the
  scopes of `CLAUDE.md`; documentation goes in the commit of the change.
- Run `mise run ci` before each commit that touches both sides; the
  server-only tasks may run `mise run ci:server` plus
  `npm run check:contract` in `client/`.

## Review Focus

1. A French browser opening a server that has no language yet: the
   first device stores `fr`, the UI stays French, and no `PUT` follows
   on the next connect (Task 6 test
   `null_language_puts_the_browser_language_once`).
2. A server unreachable at start: the cached language stays, nothing is
   written (Task 6 test `failed_get_keeps_the_cached_language`).
3. A browser whose preferred languages are `fr-CA`, `de` or empty:
   `fr-CA` resolves to `fr`, `de` and empty to `en` (Task 6 test
   `browser_language_matches_the_primary_subtag`).
4. A stored language row written by hand as `de`: the API answers 500,
   it does not silently fall back (Task 1 test
   `invalid_stored_language_is_an_error`).
5. A failed `PUT` from the picker: the UI keeps the current language and
   shows the error message (Task 6 test
   `choose_keeps_the_language_when_the_put_fails`).
