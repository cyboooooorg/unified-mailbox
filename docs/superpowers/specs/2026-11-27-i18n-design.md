# Internationalization design

Issue: #62. Related: #10 (domain model), #15 (client skeleton), #19
(classifier port and Claude API adapter), #20 (Claude Code CLI
classifier), #25 (tags), #54 (settings from the client), #77 (visual
style), #2 (phase 0).

## Intent

Make the whole app translatable from the start instead of retrofitting
it. The server speaks in stable codes; the client turns them into text
in the user's language. The one text the server does produce for the
user, Claude's summary and reason, is generated in that same language.
The owner uses the app in French; the repository and its base language
are English.

## Decided in #62

- The server never produces user-facing text. Domain values are stable
  English codes (`Priority::High`, `Move::Junk`, `dry_run`); the API
  returns them and the client translates them.
- Server errors carry a stable code plus structured parameters, never a
  sentence for the user.
- Default tags have a stable key; the client shows a translated name
  until the user renames the tag. A tag the user created keeps its name.
- Claude writes the summary and reason in the user's language; they are
  not translated afterwards.

## Goals

- One language setting per server, stored in SQLite, read and changed
  through the API. The client UI and the classifier both follow it.
- A client i18n layer: typed messages, English and French, English as
  base and fallback; every user-facing string of the skeleton moved to
  it.
- Date, number and relative-time formatting through `Intl`, in the
  current language.
- The contract a classifier adapter (#19, #20) follows to receive the
  language.

## Non-goals

- More languages than English and French. Adding one is a JSON file and
  a `Language` variant.
- A language per device. One user, one language: a summary written in
  French is never shown inside an English UI.
- The settings framework of #54 (overrides of environment values, export
  and import). This design adds the first setting and the table #54
  grows from.
- A language switch on `/pair`: before pairing the UI uses the cached
  language, else the browser's.
- Translating mail, or detecting the language of a mail.
- Server-generated text that goes into outgoing mail (see "Outgoing mail
  text").

## Anti-goals

- A flash of English on every start for a French user.
- A missing translation that ships unnoticed.
- Anything that needs `eval` or `'unsafe-inline'` in the CSP.

## Approaches considered

Where the language setting lives, and whether there is one or two:

1. **One server setting, stored now (chosen).** A minimal `settings`
   table and `GET/PUT /api/v1/settings/language`. UI and classifier
   follow it; `/pair` follows the browser. Pulls a small part of #54
   forward.
2. **Environment variable, read-only for the client.** Simplest, fits
   "configuration read once in `app`", but the language cannot be
   changed from the app before #54.
3. **Two settings:** UI language per device (`localStorage`), Claude's
   language on the server. Flexible, but a French summary can sit in an
   English UI and the user has two switches for one idea.

The owner chose 1.

Client library:

- **Paraglide JS, 3.x at the time of writing (chosen).** Messages
  compile to typed functions (`m.pair_submit()`): a missing key or a
  wrong parameter fails `svelte-check`, as `Record<ErrorCode, string>`
  does today. No runtime parser or `eval`, so the CSP stays strict; only
  used messages reach the bundle. Only its Vite plugin is used, not its
  SvelteKit server hooks (the app is a static SPA).
- `svelte-i18n`: ICU MessageFormat parsed at runtime, untyped keys,
  built on Svelte 4 stores. Rejected.
- `i18next`: generic and heavy for two languages and a few dozen
  strings. Rejected.

## Design

### Domain

`domain::Language`, an enum `En | Fr`, with its BCP 47 code (`en`, `fr`)
as the stable string form (`as_code`, `from_code`, as the other code
enums of the domain), and `Language::DEFAULT = En`. Its English name
(`English`, `French`) is also on the type, for the prompt
(`english_name`).

### Storage

Migration `0004_settings.sql`:

```sql
CREATE TABLE settings (
    key TEXT PRIMARY KEY,
    value TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

Key/value so that #54 adds settings without a migration each. The
`language` row holds the BCP 47 code. No row means "not set yet".

Port `ports::SettingsRepository`, typed, not key/value:

```rust
#[async_trait::async_trait]
pub trait SettingsRepository: Send + Sync {
    /// `None` until a client sets it.
    async fn language(&self) -> Result<Option<Language>, RepositoryError>;
    async fn set_language(&self, language: Language, at: DateTime<Utc>)
        -> Result<(), RepositoryError>;
}
```

The SQLite adapter implements it on the `settings` table. A stored value
that does not parse (edited by hand, or written by a newer server) is a
`RepositoryError`, not a silent default.

### Use cases

In `application::settings`:

- `get_language` returns `Option<Language>`.
- `set_language` stores it with the clock's time and, only when the
  value changed, publishes `Event::SettingsChanged` on the event bus, so
  other devices reload their settings. Setting the same value again
  writes and publishes nothing. When the stored value cannot be read
  (a code written by a newer server, after a downgrade), it still
  writes and publishes: a `PUT` is the way out of an unreadable value,
  which otherwise fails every `GET`. (Our call, after review.)
- `effective_language` returns the stored language or
  `Language::DEFAULT`: what the classifier uses.

`Deps` gains `settings: Arc<dyn SettingsRepository>`.

### HTTP API

Bearer-protected like every route but `/health` and `/pairing`.

- `GET /api/v1/settings/language` → `200 {"language": "fr"}`, or
  `{"language": null}` when not set.
- `PUT /api/v1/settings/language` with `{"language": "fr"}` →
  `200 {"language": "fr"}`. An unknown code is `422 invalid_request`
  (the existing JSON rejection path).

`LanguageDto` is its own enum in `http` (`en`, `fr`), converted to and
from `domain::Language`. The contract is regenerated in the same commit.

SSE: a new event `settings_changed` with no payload, mapped from
`Event::SettingsChanged`. Older clients ignore it (unknown types are
already dropped).

### Errors with parameters

`ErrorDetail` keeps `code` and `message`. `message` stays an English
sentence for logs and developers; the client never shows it. No error
code needs parameters yet, so `params` is not added now: the first code
that needs one adds an optional `params` object to `ErrorDetail` and a
message function that takes them on the client. (Our call, to avoid an
empty field in the contract.)

### Classifier contract (for #19 and #20)

The classifier port does not exist yet. When it does:

- Its input carries a `language: Language`, passed by the use case on
  every call from `effective_language`. A change of language applies to
  the next classification, without a restart. Stored summaries keep the
  language they were written in.
- The prompt stays in English. It gets one instruction built from the
  language: "Write `summary` and `reason` in {english_name}." Mail
  content stays fenced as untrusted data; a mail asking for another
  language is ignored like any other instruction in a mail.
- Mailbot's prompt hard-codes French (`app/classifier.py:32`): the port
  replaces that line with the instruction above.

A comment on #19 records this.

### Client

Files:

- `client/project.inlang/settings.json`: base locale `en`, locales `en`,
  `fr`, the message-format plugin, path pattern
  `./messages/{locale}.json`.
- `client/messages/en.json`, `client/messages/fr.json`: flat keys in
  snake case, prefixed by screen or module (`pair_title`,
  `status_jobs_none`, `error_invalid_pairing_code`, `job_kind_<kind>`,
  `language_name_en`…). Parameters are named (`{done}`, `{total}`);
  plurals use Paraglide variants on `Intl.PluralRules`.
- `client/src/lib/paraglide/`: compiled by the Vite plugin; generated,
  git-ignored. `prepare` and `check` compile it first so `svelte-check`
  runs on a fresh clone.
- `client/src/lib/i18n/`: the language state, the formatters and the
  sync with the server.

Locale resolution (Paraglide strategy): `localStorage`, then the
browser's preferred languages, then `en`. The server value is the truth;
`localStorage` is its cache so the first paint is already in the right
language. Sign-out (401, revoked device) keeps the cache: the last
language the user chose is a better guess for `/pair` than the
browser's. (Our call.)

Sync with the server, in the layout once a token exists:

1. `GET /settings/language`.
2. A language: if it differs from the cached one, store it and switch.
3. `null` (first device on a new server): `PUT` the language on screen,
   the one Paraglide resolved (the cached language, else the browser's,
   else `en`), so the UI does not switch. (Changed after review: the
   browser language alone would undo a cached choice.) This is a
   plain `PUT`, not a "set if unset": two devices paired within the
   same second on a new server is not a case of a one-user app, and
   the last write wins. (Our call.)
4. A failed `GET` keeps the cached language; nothing is written.

The sync runs on every connect and reconnect of the event stream (the
`onConnect` the status page already uses, which a `resync` also
triggers) and on `settings_changed`, so a missed event is caught up on
the next connection. Switching changes `<html lang>` and re-renders the
messages without a page reload.

A language picker on the status page: a `<select>` with each language
named in itself (`English`, `Français`, not translated), which `PUT`s
the choice and switches on success; on failure it shows the error
message and keeps the current language. Plain CSS, minimal, until #77.

Strings moved:

- `src/lib/api/errors.ts`: `Record<ErrorCode, () => string>` over
  message functions, so a new code still fails `npm run check` until it
  has a message. `GENERIC_ERROR` becomes a function.
- `src/routes/pair/+page.svelte`, `src/routes/+page.svelte`,
  `src/routes/+layout.svelte`: every visible string, including
  `Loading…`, the stream states, `This device`, the job line
  (`{done} of {total}`, `{failed} failed`).
- Job kinds are codes: a known kind gets its `job_kind_<kind>` message;
  an unknown one (newer server) shows the raw code.

`Unified Mailbox` is the product name and is not translated.

### Formatting

`src/lib/i18n/format.ts`, on the current locale and the browser's time
zone:

- `formatDate`, `formatDateTime` (`Intl.DateTimeFormat`, medium date,
  short time);
- `formatNumber` (`Intl.NumberFormat`), used for job counters;
- `formatRelative` (`Intl.RelativeTimeFormat`, `numeric: "auto"`), from
  a timestamp and a `now`, picking the largest unit under which the
  difference is at least 1.

The server keeps sending UTC RFC 3339 timestamps. The skeleton shows no
date yet; the functions are ready for phase 3 screens.

### Default tags (#25)

Not built here. Recorded for #25: a default tag has a stable `key` and
no stored name until the user renames it; the client shows
`tag_default_<key>` while the name is empty. A comment on #25 records
this.

### Outgoing mail text

Mailbot writes French into mail it sends: the reply and forward headers
(`Le …, X a écrit :`, `Message transféré`, `app/compose.py:106-147`) and
the GDPR letters, which carry their own language per request
(`app/gdpr.py`). These are exceptions to "the server never produces
user-facing text": the text is part of a mail, built on the server. The
feature that ports them takes the language from `effective_language`
(or, for GDPR letters, from the request). An issue records it.

## Tests

Server:

- `Language`: `as_code` and `from_code` round-trip, an unknown code is
  an error.
- SQLite: no row → `None`; set then get; set twice keeps the last; an
  unparsable stored value → error.
- Use cases: `set_language` publishes `SettingsChanged` on a change and
  nothing when the value is the same; `effective_language` falls back to
  `En` when unset.
- HTTP: `GET` unset → `null`; `PUT` then `GET`; unknown code → 422
  `invalid_request`; both routes → 401 without a token; the event goes
  out as `settings_changed`. The contract test covers the new schemas.

Client:

- `en.json` and `fr.json` have the same keys and, per key, the same
  parameter names.
- `errors.ts`: a known code gives its message in each language; a
  malformed body gives the generic one.
- Sync: language returned → switch and cache; `null` → `PUT` of the
  language on screen; failed `GET` → cached language kept, no `PUT`;
  `settings_changed` and a stream (re)connect → sync again; sign-out
  keeps the cached language.
- `format.ts`: fixed dates and numbers in `en` and `fr` (`1,234` vs
  `1 234` with the narrow no-break space), relative times across unit
  boundaries.
- Job kind: known kind translated, unknown kind shown raw.
